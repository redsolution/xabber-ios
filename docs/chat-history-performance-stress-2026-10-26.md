# Чат: открытие, история, прокрутка и поиск на устройствах

Дата: 2026-10-26. Проверена установленная `xabber.ios` (1.0/build1) на iPhone 12 Pro/iOS 26.6.1 и iPad Air 11 M3/iPadOS 26.7.1. Основное приложение не пересобиралось и не переустанавливалось. Данные, ключи и кэши сохранялись; сообщения не отправлялись и не удалялись.

## Открытие несинхронизированных чатов

До первого открытия двух обычных чатов iPhone read-only снимок Realm подтвердил отсутствие canonical archive coverage record, generation 0. Это реальное исходное bootstrap-состояние, но не доказательство отсутствия любых локальных сообщений: их исходное число не снималось. Debugger отсоединён до измерений.

| Измерение | Результат | Граница доказательства |
| --- | --- | --- |
| Первый чат: native open_request → guarded content_receipt | 1.742 s, n1 | Содержимое принято UI; не отдельное время ответа сервера |
| Тот же чат:3 повторных открытия → content_receipt | 245.646/229.415/234.958ms; median 234.958 ms | Внутренние signposts одного чата |
| Повторные открытия → guarded stable_frame | 854.501/835.833/840.966ms; median 840.966 ms | Для первого открытия stable_frame не захвачен |
| XCTest: первое наблюдаемое содержимое двух чатов | 4.774/4.708 s | Включает tap, XCTest idleness, AX snapshot и polling |
| XCTest:3 повторных открытия каждого чата | 3.755–3.914s, n6 | Нельзя трактовать как чистое время отрисовки |

Оба первых открытия и все 6 повторных завершились реальным содержимым без наблюдаемого pending. Legacy unscoped first-frame181ms не используется как завершение bootstrap: он предшествует guarded content_receipt.

## Устойчивость при прокрутке

На каждом устройстве отдельный законченный прогон:20 жестов к старой истории,20 обратно,60 с чередованием направлений. Итого 100 на устройство,50 в каждую сторону. Каждый десятый жест сопровождался проверкой неизменяемого AX snapshot; start/end сохранены отдельно.

| Проверка | iPhone | iPad |
| --- | --- | --- |
| Прогон 100 жестов | PASS | PASS |
| Здоровые контрольные точки | 10/10 | 10/10 |
| Реальных видимых сообщений на точке | 11–15 | 13–16 |
| Различных canonical IDs, включая начало/конец | 41 | 76 |
| Наблюдавшиеся даты | 06.11.2025–23.09.2026 | 20.10.2026 |
| Дубликаты / pending / skeleton / ошибки на точках | 0/0/0/0 | 0/0/0/0 |
| Проверки пустого draft с сохранением composer | 11/11 | 11/11 |

Это проверка устойчивости при 100 быстрых flick-жестах с паузами XCTest, а не сертификация непрерывной ручной «яростной» прокрутки или FPS. Промежуточные краткие состояния между checkpoints не исключены. Даты и число уникальных ячеек не означают достижение конца серверного архива.

В native trace iPhone записано 3963 интервала MainThread `chat.scroll_processing`: median 0.351 ms, p95 0.563 ms, max 1.949 ms. App phases присутствуют только в поздней части захвата; первые 40 жестов действительно меняли окна/даты сообщений, но соответствующие native phases отсутствуют по неизвестной причине. Эти короткие callbacks не равны времени полного кадра.

## Загрузка истории

На контрольных точках загруженное содержимое сохранялось при движении в обе стороны; необъяснённых пустых окон и повторяющихся canonical IDs не обнаружено. Получить отдельные сопоставленные MAM transport/persistence/page-apply интервалы не удалось: в trace нет нужных phase/lease correlation, в существующем контейнере приложения не найден файловый лог. Скорость серверной подгрузки страницы и полнота серверного архива остаются **не измерены**.

В trace открытия присутствуют MainThread datasource-apply wall intervals около 110–117ms. Это диагностический кандидат на отдельный performance audit; interval может включать ожидание CATransaction completion и не доказывает непрерывную CPU-блокировку. Release FPS/hitch gate здесь не запускался.

## Поиск

iPad, обычный чат, запрос `test`:10/10 циклов query → list → message jump → Cancel прошли, выбранная идентичность сообщения и пустой draft сохранены. Counter во всех циклах 1 of 1; обе стрелки проверены выключенными, переход между несколькими результатами этим прогоном не покрыт. Две видимые query-matching ячейки при одном результате сами по себе не доказывают дефект индекса: AX не показывает stored body, eligibility и MAM dedup identity.

XCTest observed upper bounds на iPad, median(n10): submit→counter 2.400 s, list→row 3.380 s, row→conversation 3.894 s. Они включают автоматизацию и не являются чистыми временами поиска/анимации.

iPhone, `gallery`: первый запрос не дал наблюдаемого terminal counter за 36.629 s от submit; поздний inspect подтвердил query в поле и Calendar-only панель без counter/loading/empty/error. Сценарий остановлен с 0 завершённых циклов. Код рисует такую панель и при idle, и при нулевом результате, поэтому это **не доказательство зависшего backend-запроса**. Пользователь не получает ясного сообщения о результате; требуется отдельно различить completed-zero и unadmitted/unfinished query. Cancel успешно восстановил прежний anchor.

iPhone, контрольный текстовый запрос `chat`: counter 1 of 18, сообщение с совпадением видно; submit→counter 2.809 s(XCTest upper bound). Enabled Previous существует в AX с корректной frame, но не виден на screenshot и не hittable в течение 8 s. Повтор с исправленным observer, проверяющим hittable только у доступного направления, воспроизвёл отказ. Обычный перезапуск app без очистки данных(PID 4930→5638) и свежий поиск повторили тот же отказ. Это подтверждённый дефект управления multi-result поиском(3 наблюдения, включая новый процесс); соседний результат и обратный переход через стрелки не пройдены.

Отдельный явный list-only прогон прерван оператором после 232 s: получены 1 of 18 и видимые строки списка, но result-row tap ещё ожидал idle. Завершённых циклов 0, jump/Cancel этим прогоном не подтверждены. В логе три 60-секундных ожидания XCTest animation-complete; это не backend latency и не доказанное падение приложения. Неполный result bundle не позволил экспортировать attachments; сохранены компактный stage/log audit и отдельные завершённые failure-снимки. Отдельный финальный Cancel прошёл; query закрыт, обычный чат Andrew восстановлен. iPad возвращён в исходный OMEMO чат по точной QA3 строке.

Ранее отдельно подтверждённый переход OMEMO→regular через ContactInfo Search остаётся открытым дефектом и описан в [функциональном отчёте](chat-screen-device-qa-2026-10-26.md). В текущем поисковом stress использовались обычные чаты.

## Проверка и артефакты

Использован отдельный временный подписанный XCUITest runner, активирующий установленную app. Он собран успешно; устройства проверялись через `test-without-building` с конкретными hardware UDID. Production/test source репозитория не менялись. Предсуществующие dirty project/scheme/OMEMO/UI-test файлы сохранены. После намеренного перезапуска один action открыл чат, но его диагностическая live-индексация AX попала в нормальную замену datasource и упала; повтор open-row при уже открытом чате также остановился на guard. Это отдельные ошибки наблюдателя, не ошибки открытия приложения.

Незаконченные попытки исключены из завершённых 100: первый тяжёлый iPad runner получил SIGKILL после 20 жестов (падение основного приложения не доказано), light retry остановился на nil/empty draft несовместимости observer, ещё один старт — на устаревшем title. После исправления временного observer/configuration полный прогон прошёл. Первый iPhone search старт с длинным ID остановился до запроса из-за XCTest 128-character query limit; последующий stale viewport guard также остановился до запроса. Отдельно устранено избыточное требование hittable у выключенной стрелки; повтор всё равно подтвердил недоступность включённого направления. Эти failures не классифицируются как продуктовые.
