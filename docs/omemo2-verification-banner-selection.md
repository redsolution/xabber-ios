# Current verification sessions in native banners

During phone/web QA a new verification request reached the current phone resource, while Settings/Devices still showed an older close-only “In process...” banner. The three native banner readers selected the first retained session rather than a current live exchange. A dedicated test-first run reproduced wrong-session selection and missing actions in Settings, own Devices and contact Identity Verification.

The readers now share read-only selection scoped to the account, peer and current positive local OMEMO SID. They use the existing XEP-TRUST manager's role/state pairs, unexpired deadline and strictly newer numeric request timestamp precedence; equal timestamps preserve existing order. Terminal, unknown, old-protocol and prior-local-device rows cannot hide a current request. Missing account or nonpositive local binding supplies no selected session.

An incoming request exposes **Proceed to Verification**; an accepted responder session exposes **Show the code**; a challenged initiator session exposes **Enter the code**. Existing intermediate states remain waiting. When no live session remains, unverified devices can show the ordinary Verify prompt. Button accessibility identifiers and normal protocol action handlers remain intact.

Selection does not delete retained rows, accept/reject requests, change expiration, create trust, reset keys or modify cryptographic sessions. Existing identity and protocol admission still govern every action. No timeout or trust assertion was relaxed, and no verification code or private state is logged.

Initial RED: 10 methods executed against unchanged controller sources with 21 expected assertion failures and 0 unexpected failures. Three further cases were written before production but were not separately run RED. Focused verification then passed 13/13. The first related gate passed 151/151 across nine classes with app/push/test build, including actual controller/button actions, real native KEX/ratchet and protected-byte preservation, existing trust interop, XEN transport, device projection, Settings and quit flows. Two additional missing-account/nonpositive-binding regressions were added after review against the unchanged guard. The final related gate passed **153/153** across the same nine classes (including **15/15** banner methods), 0 failures, with app/push/test build. Source hashes remained unchanged throughout that action. Runs overlap and are not additive distinct coverage.

Private evidence is in vault `debug/2026-11-03-verification-banner-selection/`. Original-tree integration passed **15/15** banner tests with app/push/test build. The six-file patch was staged separately; all 22 prior WIP files were preserved, including the exact prior project contents after subtracting four task additions. Installation/retest on phone/tablet remains pending. The complete three-client acceptance matrix, including the separate web cancellation issue, is not established by these simulator tests.

## Normal Devices navigation follow-up

After installation, the ordinary Verify action returned. A genuine native-initiated exchange then reached `receivedRequestAccept`, but Devices still showed no Enter code action. Normal Settings navigation calls `configure(for:)` without separately setting `owner`; that method had set only `jid`. Loading used `jid`, while action rendering and account lookup used the empty or previous `owner`.

Devices configuration now assigns the requested account to both fields before reading or rendering. This adds one production line and changes no protocol, trust, expiration or cryptographic state. Five new tests use the actual configuration path with empty/stale owners and the actual Settings navigation, covering incoming Proceed, responder Show code and initiator Enter code actions. The earlier fixtures explicitly set owner and had missed this route boundary.

The five new cases executed against unchanged production with **15 expected assertion failures and 0 unexpected failures** before the one-line correction. The complete **20/20** banner suite and relevant Settings/device-security/quit gate passed **56/56**, with app/push/test build and unchanged source hashes.
